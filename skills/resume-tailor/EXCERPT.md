# Resume Tailor (excerpt)

> **Public edition — excerpt.** The production skill is several times this size; this excerpt keeps the three-phase core and the exit sequence ("Grade and write back"), because those two structures carry the design. Re-authored in English; the candidate is referred to as *the candidate*. The exit-gate rubric it hands off to is published beside this file as `graders.md`.

## Purpose

Tailor a resume for one job description through a real hiring manager's eyes — making the page richer, clearer, and more convincing, not compressing it into keyword paste. The work is deep reframing of what the candidate actually did and can defend in an interview, so the hiring manager's first read lands in the correct pool: they can see which underlying capabilities are already proven, and how those capabilities enter this JD's daily work objects, stakeholders, handoffs, and outputs.

The skill is not hunting for a resume an average reader wouldn't dislike. It is hunting for the hiring manager who will book the interview *because* the candidate turns AI collaboration into steadier, more verifiable, more transferable work quality. So AI-assisted, source-grounded workflow evidence is stably protected — but on every run it must be translated into that JD's role-native work quality. AI is a method that helps the right reader see work quality faster; it is never the headline identity.

## The three-phase core

```text
Phase A | BECOME THE HM      Read only the JD / routing brief / stakeholder research.
                             Stand in the hiring manager's position before touching
                             any candidate material.
Phase B | SET THE PAGE GOAL  Define the page's HM decision thesis (below).
Phase C | TRANSLATE          Open the section rules and translate section by section —
                             bottom-layer capability first, JD language second.
```

**Phase A — become the HM.** Write down how this hiring manager screens: what friction this line of work resolves daily, who gets pulled into interviews, who gets cut, which nouns route a candidate into the wrong pool. Until the HM read is stable, the candidate's resume, master sources, and proof libraries stay closed. Otherwise the AI starts finding seats for the candidate's highlights instead of reading who the job wants. (This is the same evidence-blinding principle as the routing skill, applied one stage later.)

**Phase B — set the Page Goal.** Not an internal slogan — the page's HM decision thesis: how should the hiring manager read the candidate within 30 seconds, why would they book the interview, and what is the candidate's first credible operating move after joining? The Page Goal states: which correct pool the page attacks; which transferable capability primitives the candidate's true stories can actually catch; what leads the page and what stays support proof; which wrong-pool read, overclaim, or borrowed noun must be avoided; and which gap is structural — to be named, never patched with wording. Every later decision is measured against it: if a change doesn't help the HM land the correct-pool read faster or see the first operating move clearer, don't make it.

**Phase C — translate from the bottom layer.** Not "rewrite each section in JD words." Take what the candidate truly did, unpack it into underlying capabilities, then translate into this JD's daily work objects, stakeholders, handoffs, and outputs. Use the routing brief's capability map: ask which true story has handled the same *judgment shape* — then, and only then, render it in correct-pool language. Evidence that can't map directly but proves a similar working posture becomes support proof. Evidence that would raise the claim ceiling becomes a named structural gap or a lowered claim. Never start from "which keyword does this JD sentence want."

Good tailoring reduces the hiring manager's translation burden: reading a true story, they immediately see what capability it proves and why this JD buys it. The candidate is early-career; the frontstage language must read as trainable-and-can-carry-this-lane — never seniorized, never overclaimed.

## AI visibility (three tiers, one test)

AI / workflow evidence follows the routing brief's `role_ai_relevance` — but "the JD doesn't mention AI" is never misread as "hide the AI." Visibility has exactly three tiers:

- **Foreground** — the JD explicitly buys AI adoption, workflow design, or AI-assisted analysis: AI may lead a label or bullet, still landing on role-native work objects and outputs.
- **Support** — the JD is silent but the work needs analysis, documentation, review, handoffs, reporting: AI stays visible but bound to work quality (e.g. *"source-grounded workflow checks"*), never as identity.
- **Backstage** — AI wording would crowd out stronger proof, cause an ownership overclaim, or hit an employer restriction: keep the underlying method (validation, reviewable records, handoffs), compress the tool names.

Before any AI line enters the resume, it passes a three-question translation test: **(1)** which role-native work object does AI make steadier? **(2)** what is the defensibility mechanism — source context, success criteria, validation, review boundary? **(3)** what handoff-ready output results? No answer → the line drops a tier. A tool name with enthusiasm and no beneficiary always fails.

One sentence governs it all: **AI as working method, not job identity** — don't let it steal the page because it's novel, don't hide it because the JD is silent.

## Grade and write back — the exit sequence

```text
initial production draft
  -> draft reframe check          (compare against 2-3 trusted mature resumes;
                                   absorb angles, never their identity systems)
  -> verified revision
  -> clean-agent cold read        (a fresh agent, blind to this session, reads
                                   the draft as a market reader; its output is
                                   blind-spot input, not an edit list)
  -> final grader                 (the 7-check exit gate — see graders.md)
  -> write back                   (final resume + a decision-trace analysis file
                                   + tracker milestone, in the same turn)
```

Three properties make this sequence worth its cost:

1. **The cold reader is clean.** It did not participate in routing or drafting, so it cannot inherit this session's rationalizations. It answers one question: *who does this page look like to someone with no context?* Its findings are absorbed only when they help correct-pool reading without breaking the page's identity system or adding indefensible claims.
2. **The grader gates, it doesn't re-edit.** The exit rubric checks and points to authority definitions; it is forbidden from inventing new standards at the door. Any fail routes back to the owning definition.
3. **Write-back is part of done.** The final resume, the decision-trace file (source decisions, Page Goal, capability matching, per-section trace, cold-read results or the reason it was skipped, grader result), and the tracker milestone land in the same turn — or the work counts as unfinished.
